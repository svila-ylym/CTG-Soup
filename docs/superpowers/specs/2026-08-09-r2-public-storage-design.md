# Cloudflare R2 Public Storage Design

## Goal

Store user-uploaded public images, including avatar candidates, in the configured Cloudflare R2 bucket and serve them through the configured public custom domain. Keep credentials out of source control and out of the browser.

## Scope

- The existing authenticated `POST /api/uploads/images` endpoint remains the only upload entry point.
- Public user uploads handled by that endpoint move to R2 in production.
- Avatar records continue to reference `UploadedAsset`; no database migration is required.
- Private system-message and email-campaign attachments remain in `PRIVATE_STORAGE_DIR`.
- Frontend bundle assets remain part of the frontend build and are not copied to R2.
- Existing database rows with local `/storage/...` URLs continue to work while local public storage is mounted.

## Configuration

All storage selection and R2 settings are backend environment variables:

- `PUBLIC_STORAGE_BACKEND`: `local` for development/test or `r2` for production.
- `R2_ENDPOINT_URL`: account-specific S3-compatible endpoint, without a bucket suffix.
- `R2_BUCKET_NAME`: target bucket name.
- `R2_REGION`: `auto` for Cloudflare R2.
- `R2_ACCESS_KEY_ID`: bucket-scoped S3 access key ID.
- `R2_SECRET_ACCESS_KEY`: matching S3 secret access key.
- `R2_PUBLIC_BASE_URL`: HTTPS custom-domain origin used to build public object URLs.

`backend/.env.example` contains placeholders only. Real values belong in the deployment's untracked `backend/.env`. The Cloudflare User API token is not used by the application. Production credentials must have Object Read & Write permission limited to the selected bucket.

When `PUBLIC_STORAGE_BACKEND=r2`, configuration validation rejects missing credentials, an endpoint containing a path/bucket suffix, a non-HTTPS public base URL, and a public base URL containing a path, query, or fragment. Local mode does not require R2 values.

## Architecture

Create a focused public-storage service with a small interface:

- `put(key, content, content_type)` stores an object.
- `delete(key)` removes a newly-created object during compensation.
- `public_url(key)` returns the stable browser URL.
- `name` reports `local` or `r2` for the upload response.

The local implementation preserves current development behavior. The R2 implementation creates a boto3 S3 client using the environment-provided endpoint, region, and credentials. R2 calls run in a worker thread so the async upload route does not block the event loop.

The upload route continues validating MIME type, filename extension, and size before storage. It generates the existing `images/<uid>/<uuid>.<ext>` key, stores the object, then inserts `UploadedAsset` with the R2 custom-domain URL. Existing frontend callers and avatar selection require no contract changes.

## Error Handling

- Validation errors remain HTTP 400 responses.
- Storage configuration or R2 write failures return HTTP 503 with a generic Chinese message; provider details and credentials are never returned.
- No `UploadedAsset` row is created when object storage fails.
- If the database commit fails after upload, the route attempts to delete the new object and then re-raises the database error.
- A cleanup failure is logged without hiding the original database failure.

## Public Access And CORS

The application uploads server-to-server. Browser PUT permissions and presigned URLs are not required. Normal `<img>` display through the public custom domain does not require upload CORS. Cloudflare must have the custom domain active with valid TLS and public GET/HEAD access for the bucket.

## Security

- No R2 secret is committed, logged, returned by an API, or sent to the frontend.
- The already shared credentials must be revoked and replaced before deployment because chat disclosure makes them compromised.
- Object keys are generated by the backend and cannot be selected by clients.
- Existing upload type and size validation remains in force.

## Verification

- Unit tests cover conditional configuration validation and public URL construction.
- Storage tests use a mocked S3 client; leaked or production credentials are never used.
- Upload API tests verify successful R2 metadata, storage failure without a database row, and database-failure cleanup.
- Existing focused backend tests and the frontend production build run before the PR is updated.
